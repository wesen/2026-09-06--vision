A good 4–5 week lab is five incremental projects, each producing a working system and feeding directly into the next one. The final project should be mostly integration, not a completely new problem.

The current Qwen3-VL-Embedding-2B is well suited to this curriculum because it supports text, image, video, and mixed multimodal inputs in one embedding space, with task-specific instructions. There are also community MLX 4/6/8-bit conversions small enough for your M1/64 GB.

Project 1 — Build a local semantic video-search engine

Goal: understand embeddings, similarity search, video chunking, and multimodal retrieval.

Start with 10–20 short videos. Divide them into 5–10 second chunks.

video
  ↓
chunks
  ↓
Qwen3-VL-Embedding-2B
  ↓
vectors
  ↓
LanceDB / NumPy
  ↓
text query
  ↓
top-K video chunks

Example queries:

"worker approaches machine"
"person opens a door"
"machine with rotating parts"
"worker picks up a tool"

Implement cosine similarity yourself first:

$$ s(q,v)=\frac{q^\top v}{\|q\|\|v\|} $$

Then move to a vector database.

Lab concepts

Learn:

vectors and norms
cosine similarity
normalization
embedding dimensions
top-K retrieval
frame sampling
chunk length
recall vs precision
shared multimodal embedding spaces
Experiment

Compare:

5-second chunks
10-second chunks
20-second chunks

and:

1 FPS
2 FPS
4 FPS

Measure which combination retrieves events best.

Deliverable

A command like:

python search.py \
  --video-dir ./videos \
  --query "worker opens machine guard"

Output:

1. machine03.mp4  02:13-02:23   0.81
2. machine01.mp4  04:31-04:41   0.76
3. machine03.mp4  07:12-07:22   0.71

Success criterion: given 10 test queries, the correct clip appears in top-5 at least most of the time.

Task:
Represent visual evidence concerning machine operating state.

Create separate embeddings for:

machine state

safety condition

for the same video chunk.

Recognition by competing hypotheses

Create text embeddings for:

H1 = "machine is running; rotating parts remain in motion"
H2 = "machine is stopped; moving parts are stationary"

Then evaluate:

$$ s_{\text{run}}=\cos(v,E(H_1)) $$ $$ s_{\text{stop}}=\cos(v,E(H_2)) $$

and define:

$$ D=s_{\text{run}}-s_{\text{stop}} $$

This is more informative than simply checking whether similarity exceeds one arbitrary threshold.

Project 3 — Temporal memory: events and states across chunks

This is where the project stops being ordinary video search.

The objective is:

Understand an event whose meaning depends on what happened previously.

Example:

chunk 31
machine running

chunk 32
machine running

chunk 33
worker approaches

chunk 34
worker opens guard

The important fact is:

machine still RUNNING
when guard was opened

even though that information does not exist entirely inside chunk 34.

Build two persistent abstractions.

Events
{
  "type": "worker.opens_guard",
  "worker": "worker_2",
  "machine": "press_1",
  "time": 184.7,
  "confidence": 0.84

States
{
  "entity": "press_1",
  "property": "state",
  "value": "RUNNING",
  "start": 160.2,
  "end": 188.1,
  "confidence": 0.88
}

Store these in SQLite.

Then queries become temporal rather than vector-only:

What was press_1.state at t = 184.7?

Answer:

RUNNING
Add hysteresis

Don't let this:

STOPPED

STOPPED

happen because of noisy frame classification.

       ↓

Even simple IDs:

Project 4 — Temporal DSL + recursive VLM investigation

This is probably the most interesting lab academically.

Users should no longer write Python.

They write:

Alert if a worker opens the machine guard without stopping the machine first.

A VLM/LLM converts it to DSL:

rule guard_requires_stop {

    bind worker W
    bind machine M

    trigger:
        W opens_guard M

    require:
        M.state == STOPPED
        continuously_for >= 2s
        before trigger

    lookback:
        30s
}
Build a parser

Use something like Lark or a strict JSON/Pydantic AST.

Compile:

DSL
 ↓
AST
 ↓
temporal query plan
 ↓
event/state database

Do not execute model-generated Python.

Then introduce uncertainty

Suppose:

machine state = UNKNOWN
confidence = 0.54

The rule engine should not immediately alert.

Instead initiate an investigation:

trigger event
    ↓
missing predicate
    ↓
retrieve nearby evidence
    ↓
ask VLM focused question
    ↓
update facts
    ↓
reevaluate rule

Give the investigator restricted tools:

LOOK_BACK(seconds)

LOOK_FORWARD(seconds)

RESAMPLE(start, end, fps)

QUERY_STATE(entity, time)

SEMANTIC_SEARCH(query, start, end)

ASK_VIDEO(question, start, end)

FINISH(...)

Example:

Step 1
"Did machine P1 stop before 184.7?"

        ↓ uncertain

Step 2
Retrieve 170–185 sec at 1 FPS.

        ↓ possible transition at 181 sec

Step 3
Resample 179–185 sec at 4 FPS.

        ↓

Step 4
VLM:
"Spindle becomes stationary around 182.9 sec."

        ↓

rule engine calculates

184.7 - 182.9 = 1.8 sec

Rule requires:

$$ 2.0\text{s} $$

Therefore:

VIOLATION

The important architectural lesson:

The VLM discovers facts; your deterministic code decides whether the rule passes.

Deliverable

Natural-language input:

"The press must be stopped for at least 3 seconds
before anyone reaches through the guard."

Generated DSL, executable temporal rule, evidence retrieval, and final decision.

Success criterion: successfully handle at least three rules that require recursive evidence gathering.

2. Worker reaches into machine while machine is running.

Some should be simple:

Some should be temporal:

Some should use absence:

Build the corpus from a simulator state machine

Don't start by animating arbitrary videos.

First define the world model.

For example:

MACHINE
    STOPPED
    STARTING
    RUNNING
    STOPPING

GUARD
    OPEN
    CLOSED

WORKER
    IDLE
    APPROACHING
    PRESSING_STOP
    OPENING_GUARD
    REACHING_INSIDE
    CLEANING
    LEAVING

Then define legal transitions:

STOPPED → STARTING → RUNNING
RUNNING → STOPPING → STOPPED

and events:

worker.press_stop(machine)
worker.open_guard(machine)
worker.reach_inside(machine)
worker.clean(machine)

Now the rule you eventually want to evaluate becomes deterministic:

IF
    worker opens_guard machine

THEN REQUIRE
    machine.state == STOPPED
    for at least 3 seconds previously

The engine controls the animation, but the state machine creates the ground truth.

Generate scenarios, not videos

Create a scenario generator.

For example:

scenario: guard_opening

initial:
  machine: RUNNING
  guard: CLOSED

timeline:
  - at: 4.0
    worker: approach_machine

  - at: 7.0
    worker: press_stop

  - at: 9.5
    machine: STOPPED

  - at: 13.0
    worker: open_guard

This one is valid because:

$$ 13.0-9.5=3.5s $$

If the rule requires three seconds, it passes.

Then automatically mutate it:

- at: 11.0
  worker: open_guard

Now:

$$ 11.0-9.5=1.5s $$

so this is a violation.

The resulting videos could look almost identical.

That's extremely valuable.

You effectively get:

$$ DSL\ rule \rightarrow LLM\ test\ generation \rightarrow VirtualHome \rightarrow video + truth $$

That's substantially less work than building Unity scenes yourself.

6. Second choice: AI2-THOR

AI2-THOR is another strong option.

It already contains interactive household scenes and exposes exact object metadata. Objects can be:

open / closed
on / off
dirty / clean
broken
filled
moving
etc.

For example, ToggleObjectOn / ToggleObjectOff modifies a visible appliance state, and isToggled in the metadata gives you authoritative ground truth.

Python:

event = controller.step(
    action="ToggleObjectOff",
    objectId=stove_id
)

assert event.metadata["objects"][i]["isToggled"] == False

AI2-THOR officially supports macOS and installs through Python.

The disadvantage

It's primarily an embodied-agent simulator.

So you often see:

camera / robot viewpoint

rather than:

third-person human doing action

For your VLM video-recognition work, that's less ideal.

I'd choose:

VirtualHome → human procedural activity

AI2-THOR → object-state reasoning

9. ML-Agents probably isn't what you want

Unity ML-Agents does provide trained agents and over a dozen sample learning environments.

But for your evaluation corpus, I would not use RL initially.

An RL agent introduces randomness:

same test
    ↓
different movement
    ↓
possibly different state

Whereas scripted behavior gives:

seed 392
    ↓
same scenario
    ↓
same violation
    ↓
reproducible evaluation

You want deterministic agents first.

Later, adding ML-Agents is interesting for testing whether your video reasoning system survives naturally varying trajectories.

Habitat 3.0 is probably the newer thing you're looking for

Habitat 3.0 was explicitly designed as a human + avatar + robot co-habitation simulator.

It gives you humanoid avatars with different appearances, programmatic humanoid control, navigation, object interaction, motion policies, mocap support, and even the ability to use text-to-motion generated movements.

Conceptually:

Python
   │
   ▼
Habitat
   │
   ├── apartment
   ├── objects
   ├── humanoid
   ├── robot
   │
   ▼
behavior/motion policy
   │
   ▼
humanoid walks / reaches / interacts
   │
   ├── RGB video
   ├── depth
   ├── semantic information
   └── simulator state

This is much more modern than VirtualHome's animation system.

And importantly, Habitat-Sim supports macOS, and its recent build/release work explicitly includes M1 Mac CI changes. The headless EGL mode doesn't work on macOS, but normal displayed execution does.

So I would seriously test this first.

The downside

VirtualHome has an exceptionally convenient abstraction:

[Walk] fridge
[Open] fridge
[Grab] milk

Habitat is more of a robotics/embodied-AI framework.

You may need slightly more Python orchestration:

human.walk_to(...)
human.pick(...)
human.place(...)

rather than writing a one-line activity program.

But you're still nowhere close to programming an engine.

TDW is another surprisingly good Mac choice

ThreeDWorld / TDW deserves more attention for your application.

It runs on:

macOS
Windows
Linux

and has humanoid agents called Replicants.

Replicants already support:

turn
move
move_to
reach
grasp
drop
look_at

play animations

with built-in IK and prerecorded animation support.

So you can write:

worker.move_to(machine)

worker.move_to(guard)

You can have multiple Replicants acting concurrently.

And attach cameras:

             overhead camera
                    │
                    ▼

          camera 2

with automatic frame capture.

TDW also contains a substantial library of scenes/assets and supports procedural scene generation.

TDW's weakness

Its action model is somewhat lower level than VirtualHome.

VirtualHome knows semantically:

SWITCHON
SWITCHOFF
OPEN
CLOSE
WIPE
DRINK

TDW's Replicant API is more:

move

grasp
drop

So you might implement:

machine.running = False

yourself when the Replicant reaches the stop button.

For an evaluation corpus, that's actually not a huge burden.

TDW is still maintained, but in LTS

TDW's repository says it is now in long-term support, receiving minor fixes rather than major new development. Its last major listed release was v1.13.0 in May 2024.

So:

For you, I'd investigate Habitat first, TDW second.

SimWorld is even newer

SimWorld is a 2025/2026 project built on Unreal Engine 5 for physical and social agents.

It supports:

realistic worlds
LLM/VLM agents
language-based procedural generation
social interactions
custom agents
custom environments
physical reasoning scenarios.

It sounds almost exactly like:

The project is actively moving in that direction.

But its runtime currently requires Windows or Linux with a dedicated ≥6 GB VRAM GPU. macOS isn't supported.

So keep it on the radar, but not for this lab.
